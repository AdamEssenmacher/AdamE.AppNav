# AppNav with SwiftUI and OAHU

The managed host targets .NET 11 for iOS. The Swift package provides an iOS 17+ renderer for one window with a linear stack, a tab host or a [split](#splits), plus one sheet with its own stack. The probe builds against AppNav from this checkout and OAHU `0.1.0-preview.g7a56b3ba`.

The floor follows the pinned OAHU runtime, which requires iOS 17. The sources also build for iOS 16, and the floor drops to 16 with the move to an OAHU runtime that declares `.iOS(.v16)`. The zoom and `.native(style)` transitions need iOS 18. On earlier releases they fall back to the automatic push. Splits use `NavigationSplitView(preferredCompactColumn:)` and need iOS 17 whatever the package floor: on an earlier release the host does not report `PresentsSplits`, so the presenter refuses a split before it stages anything. The simulator suite runs at iOS 18 and later. It doesn't cover iOS 16 or 17.

## Integrate

1. Reference [AdamE.AppNav.SwiftUI.csproj](AdamE.AppNav.SwiftUI.csproj) from the iOS app or use the `AdamE.AppNav.SwiftUI` NuGet package. The package includes its SwiftPM manifest and sources under `native/Swift`. Add [the Swift package](Swift/Package.swift) to the app's OAHU screens package. When using a packed NuGet artifact, find the Swift package at `native/Swift` inside it. Both Swift packages resolve `OahuRuntime` from `OAHU_RUNTIME_SWIFT` when set. Otherwise they look for the pinned OAHU package under `NUGET_PACKAGES`, which defaults to `~/.nuget/packages`. Set `OAHU_RUNTIME_SWIFT` explicitly when the build process cannot see your configured NuGet package directory.
2. Set up OAHU screen generation for the app's contracts. Use the hosted `INavigationShellViewModel` contract or define a shell contract that delegates `Target` and `Report` to that model. In the Swift screen, translate these generated values to `NavigationProjection` and `NavigationReading`. [The example screen](../../prototype/Shell/ProbeScreens/Sources/ProbeScreens/Screens.swift) shows the mapping and a test-only footer. The app's mounted screens specify their own titles and toolbars.
3. Initialize `OahuScreens` before scene attachment. Create one `RouteEntryLeaseRegistry` with `SwiftUIRouteEntryLeaseHost`, pass that same registry to `RouterNavigatorFactoryOptions.EntryLeases` and `SwiftUINavigationHost.Attach`, and bind the `OahuNavigationPresenter` to the router. The factory callback takes a `RouteEntry`, its lease, and a flag for a lease opened during that call. It chooses the app screen and returns its `OahuMount` plus optional cleanup.
4. Set the scene window's root controller to the host's `ViewController` before navigating. If recreating a scene while retaining the router, attach its new host and call `RefreshPresentationAsync` so the new surface witnesses the retained state. On disconnect, call `Detach`, remove the controller from the window, and dispose the host on the main thread. Dispose the navigator asynchronously when its lifetime ends.
5. Send push, deep-link, and programmatic Back intents through the router. SwiftUI owns native tab selection and Back animations. The presenter reconciles native changes after the visible stack settles.

The factory may register entry-owned resources on an open lease. Use `AfterTeardown` for view models and other resources owned by a single mount, including when rebuilding a scene whose retained lease is closed. The host runs it after OAHU disconnects the mount and before detaching the lease. If the factory throws before returning, it owns cleanup for resources created during that call.

An app requiring a policy decision before Back may supply a `NavigationBackControl` to route Back through an AppNav Back command when a guarded screen is on top. The shell replaces the system Back button on that screen and disables interactive sheet dismissal when the guarded screen is the sheet’s top entry. From an unguarded screen above it, the user can use the native Back-history menu to pop past the guarded screen, or swipe down to dismiss the entire sheet. Either action can remove the guarded screen without invoking the app’s Back request. The app should use the same managed Back command for any close buttons it adds to guarded screens.

A guarded entry never takes a destination transition such as a zoom: UIKit's interactive zoom dismissal would pop the page past its Back button, and no public API turns it off for a SwiftUI zoom. It arrives with the automatic push. The same holds for a guarded sheet or full-screen cover root, which presents without its destination transition. Whether `interactiveDismissDisabled`, which the shell already applies to a guarded modal top, would also stop a zoomed modal's interactive dismissal was not measured; the shell never zooms a guarded root, so it doesn't depend on it. `intercepts` runs on the main thread while SwiftUI builds pages, and on every display frame for the root of a collapsed split's secondary column, so it must be a cheap lookup. The default configuration observes native Back, including canceled edge gestures and the native Back-history menu.

## Native settling

When a host-owned UIKit `.fullScreen` presentation removes the hosting view from its window, `SwiftUINavigationHost` waits for the view to reattach before staging a new navigation request. The acknowledgement timeout starts when staging begins. The router commits the request after the restored SwiftUI stack supplies a matching native reading.

By default the renderer assigns complete SwiftUI paths in an animation-disabled transaction. Set `animatesSinglePushes: true` on `NavigationShell` to animate a one-entry append to the settled visible stack. The app can then use SwiftUI's matched zoom source on the tapped cover and zoom transition on the mounted destination. The app supplies the row's press and selection appearance. A branch switch or multi-entry deep link still installs its complete path without stepping through intermediate destinations. It samples the active native controller stack across consecutive frames and verifies the mounted top, controller count, observed identities, and transition state. SwiftUI may materialize intermediate pages only when exposed by Back. The shell preserves its last witnessed path for an interactive cancellation and waits for sheet removal before reporting dismissal. While a revision applies, the shell withholds native Back and interactive sheet dismissal until the native stack settles. The one exception is Back on an animated one-entry push once its page is on screen. If a Back gesture or a pop from the Back-history menu makes UIKit give back an animated one-entry push before the shell settles it, the shell takes the shorter path at once. When UIKit's stack settles without the page, it reports the push and the shorter stack as a native Back together. A cancelled gesture puts the push back. SwiftUI no longer pushes the page again. A revision that arrives during an interactive Back or sheet gesture waits until the gesture ends, then installs. Any other native pop, dismissal, or tab change that still gets through while a revision applies is taken and then undone on the next quiet frame, so SwiftUI and UIKit never disagree about the stack. After three such undos for one revision the native state stands. If the native side sits still for two seconds without showing the revision, for example under an app alert, the shell traces it, stops waiting, and releases Back and dismissal; the revision still settles if its stack appears later. The shell briefly withholds Back on a newly selected tab while AppNav accepts the selection. If a pop slipped through before a separate tab reading, the shell restores that tab’s intact stack so the selection can commit. Intermediate actions without an independent native reading cannot add a separate history entry. The controller lookup depends on SwiftUI's UIKit hosting hierarchy. The simulator suite covers iPhone navigation and the split scenarios listed below; it has no tests for iPad-specific navigation or physical devices.

The settle rules live in `SurfaceState`, which has no UIKit dependency. Run its tests on the Mac host with `swift test` from [Swift](Swift); they include randomized checks that a revision never stays applying once the native side is quiet. The tests don't use OAHU, but SwiftPM still resolves the `OahuRuntime` path dependency on macOS. Restore the iOS project first so the pinned `Oahu.iOS` package is in your NuGet package directory, or set `OAHU_RUNTIME_SWIFT`.

The iPhone simulator suite covers canceled Back and multi-pop, a direct deep link and ordinary Back traversal, retained tabs, an animated push inside a sheet, modal dismissal, guarded Back, and the managed and native Home → Game pushes. It also exercises an animated sheet presentation and replacement of the SwiftUI hosting controller during a pending push.

The split tests run with `--probe-split`.
- **Collapsed, on phones and the closed iPhone Duo simulator:**
  - a selection and a swipe back that closes the column;
  - a game switch over SwiftUI's stray compact column;
  - a selection taken back by Back;
  - a sheet over a game;
  - a guarded game root that shows the app's Back and resists the edge swipe;
  - a guard released while its root shows, which brings back the system Back and the swipe.
  - a swipe back from a page above a guarded root, which completes, after which the guard holds against the edge and content swipes.
  - an AppNav Back from a guarded root over SwiftUI's stray compact column, which closes the column through the native pop.
- **Side by side, on the open Duo sideways:**
  - a game switch, a system Back inside the game, and an AppNav Back;
  - a guarded game root with no Back of either kind.

  Both tests skip upright, where XCUITest's taps on the detail column do not reach the app; the upright overlay was checked by hand.
- **Fold:** the fold-after-pop test needs the Duo's posture driven from outside and runs only with `TEST_RUNNER_APPNAV_POSTURE=1`.
- **Plain stack:** a guarded Game page pushes without its zoom and resists the edge swipe.

Nothing covers a physical Duo or an iPad. See the [test matrix and reproduction commands](../../prototype/SWIFTUI.md).

## Splits

A window whose root is a `SplitNode` with a stack in each column renders with the system `NavigationSplitView`. Map the hosted `ShellTarget.Split` into `NavigationProjection.split` and report `NavigationReading.secondaryEntries` and `compactColumn` back, as [the example screen](../../prototype/Shell/ProbeScreens/Sources/ProbeScreens/Screens.swift) does. The projection's only branch is the primary column. The detail column shows the secondary column's stack, or the shell's empty content when there is none. The OAHU presenter projects a split only to a surface that reports `PresentsSplits`; `SwiftUINavigationHost` does, and the Compose host does not. Splits inside branches or modals, and branch hosts inside a column, are refused with `NotSupportedException` before anything is staged.

Column visibility is the system's: `NavigationSplitView` keeps its automatic visibility and its Show Sidebar button, and AppNav never treats visibility as state. On the iPhone Duo simulator's inner display the automatic visibility shows the detail column with the Show Sidebar button in both orientations. Upright, the sidebar overlays the detail; sideways, it tiles beside it. The overlay stays open after a selection, as it does in plain SwiftUI. Phones and the Duo's outer display collapse the split into one navigation stack: the primary column, with the secondary column above it while `CompactColumn` is `Secondary`.

Rows in the primary column are app navigation. Make them plain buttons that ask the router to select, with `SplitNode.Select`. A `List(selection:)` writes the selection natively and pushes the detail on a collapsed window regardless of `preferredCompactColumn`, so it fights the shell.

- Selecting over a collapsed primary column is a one-entry push. The transaction policy and destination transition apply as for a stack push, so a selection can zoom from a matched source on the row. A selection made side by side does not zoom, because SwiftUI hides a matched source while its destination shows. When a window that zoomed into a game unfolds, the shell drops the zoom, so Back no longer zooms. SwiftUI still keeps that row's cover hidden while the game it opened stays on screen.
- Back inside either column, and a collapsed window's Back from the secondary root, are native Back. The presenter reconciles them, closing the secondary column with `ClearSecondary` in the second case. A pop in the primary column beside a shown secondary column keeps that column, exactly as shown. A Back-history multi-pop from the secondary column into an earlier page of the primary column closes the column and pops the primary column in one reconciliation. A reading whose compact column is neither `primary` nor `secondary` is reported to the host's failure handler and is not reconciled.
- On a collapsed window the secondary root sits over the primary column with the system Back. A root that `NavigationBackControl` intercepts gets the app's Back button there instead. The surface also turns off the navigation stack's edge and content swipes while the guarded root is on top. It hides the system Back on every frame the root is on top, transitions included, but turns the swipes off only when the transition onto the root completes, or on the next quiet frame, so a swipe already under way, such as one returning to the root, finishes. It undoes only what it changed, when the root leaves the top, the app stops intercepting it, the window unfolds, or the shell leaves the window. Side by side, the root has no Back of either kind.
- A Back that catches an animated selection before it settles is taken back like a stack push: AppNav records the selection and then a Back that closes the column.
- Selecting another item replaces the detail column with a new `NavigationStack`.
- Folding and unfolding change no reading, so AppNav sees no navigation.

SwiftUI writes `preferredCompactColumn = .sidebar` whenever the secondary stack's path empties, even while the secondary root stays on top. The shell keeps every write, because refusing one, or writing `.detail` back while collapsed, makes SwiftUI push the secondary root a second time. Readings therefore come from UIKit's stacks alone. While both columns show, the shell writes the staged column back on a quiet frame, which changes nothing on screen and keeps a later fold on the secondary root. A collapsed window that still holds the stray value cannot pop or replace its secondary column through the binding. In that case the shell pops UIKit's navigation stack to the primary column's top, as a native Back would, and then writes the staged column.

The settle rules for splits live in `SurfaceState` with the others. A split's layout counts once it holds for two frames. A primary column the window hides settles on its path, like an unselected tab.

## Native transitions and destination chrome

Map the OAHU shell transition into `NavigationProjection.transition` for each projection. Its operation, source and destination entries, optional screen names, and source key are presentation metadata. The app chooses a shared key and namespace for the cover it marks with SwiftUI's `matchedTransitionSource`.

Pass `NavigationCustomization` when constructing `NavigationShell` to configure three native hooks:

- `transactionAnimation` returns a SwiftUI `Animation`, or `nil` for an immediate install. The renderer consults it for a verified one-entry push or pop in the visible branch or open sheet, a root-only sheet presentation, or an isolated sheet dismissal. The background branches and their mounts must remain unchanged during an in-sheet step. A new sheet with prebuilt history installs directly, as do multi-entry paths, branch switches, refreshes, rollbacks and host reattachment. The existing `animatesSinglePushes` option remains the default for pushes when a policy is omitted. User-initiated Back and sheet gestures keep their system animation.
- `transition` selects `.automatic`, `.zoom(sourceID:namespace:)`, or `.native(style)` for a destination. The native case accepts a SwiftUI `NavigationTransition` value. The shell attaches the style to the decorated page for a stack destination, or to the presented container for a sheet root. A sheet root takes a matched style only when a root-only sheet opens over the settled top of the selected branch and the transition names that page as its source; the source view belongs on that page. A style that does not need a matched view can run without a source key. A route-wide style can also configure a restored destination for a later native Back. The transaction policy still controls animation during installation. Use the dedicated zoom case with a matching `matchedTransitionSource` in the source view. Even for an immediate push, the renderer associates the push context with the exact source and destination mounts for native Back, preserves the departing view through the transition, and drops its origin after settlement. A replaced source or restore clears the corresponding match.
- `chrome` decorates the mounted view with app-owned SwiftUI presentation, such as the navigation title and toolbar. It runs when SwiftUI constructs the destination, including its initial transition build.

With the iOS 27 SDK, return `.native(.crossFade)` for a sheet root in an `if #available(iOS 27, *)` branch, then return `.automatic` on earlier releases. Enable animation for the isolated sheet presentation with `transactionAnimation`. Update any exhaustive switches over `NavigationDestinationTransition` to include the native case. [Apple’s crossfade example](https://developer.apple.com/documentation/swiftui/navigationtransition/crossfade).

When passing an already type-erased style that needs a matched source, set `requiresMatchedSource: true` so the shell checks for a live keyed origin. SwiftUI's type-erased value does not expose the underlying style.

The Fade Sheet demo crossfades on iOS 27.2. During the recorded presentation, three regions at different heights blend together over the same frames. In a separate iOS 27.0 comparison, both an AppNav push and a direct SwiftUI `NavigationLink` using `.crossFade` render with a horizontal slide. [Sheet recording](../../prototype/results/fade-sheet-ios27.mp4) · [Frame samples](../../prototype/results/fade-sheet-ios27.frames.txt).

The Game probe uses the hooks to choose a zoom from `game-cover` and attach the Game toolbar. Its comparison row uses a system view-destination `NavigationLink` inside the same typed stack. The Edit sheet uses the hooks to push Review from a matched source without changing the background branch. [SwiftUI probe](../../prototype/Shell/ProbeScreens/Sources/ProbeScreens/Screens.swift).

Use the `modalPresentation` closure on `NavigationCustomization` to select `.fullScreenCover` for a modal that fills the window, such as a camera scanner. The default is `.sheet`. Select a stable style for each modal occurrence. A full-screen cover has no swipe-to-dismiss, so its root page must provide its own close control, such as a Done button or an intercepted Back. Both presentations contain the same AppNav-managed stack and reconcile dismissal through the native observer.
